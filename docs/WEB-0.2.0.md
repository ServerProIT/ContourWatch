# Панель Контур 0.2.0

Windows-агент остаётся 0.1.2, Linux-агент — 0.1.0. Переустановка агентов для этого обновления не нужна.

## Обновление существующей панели

На ВМ панели, в каталоге репозитория:

```sh
sudo sh deploy/backup.sh /путь/к/защищённым/копиям
git pull --ff-only origin main
sudo sh deploy/up.sh
```

После запуска обновите браузер через Ctrl+F5. Существующие устройства, учётные данные агентов, история и настройки сохраняются. Прежние группы автоматически переносятся в отдельный справочник один раз. Для отката на старую панель используйте согласованную резервную копию до миграции; старая версия не поддерживает новые права и связи групп. Не удаляйте Docker volume.

## Пользователи

Для первого входа выберите «Прежний ключ доступа» и используйте уже выданный ключ администратора. Значение ключа по-прежнему не выводится в журнал. В разделе «Пользователи» создайте персональный аккаунт администратора и обычные аккаунты. Далее входите по логину и паролю. Логины нечувствительны к регистру, пароль — от 12 до 256 символов; в БД хранится scrypt с индивидуальной случайной солью.

| Возможность | Читатель | Менеджер | Администратор |
|---|---|---|---|
| Все устройства, показатели, история, события | Да | Да | Да |
| Собственный выбор колонок | Да | Да | Да |
| Устройства, группы, глобальные настройки, оповещения | Просмотр устройств и глобальных настроек | Управление | Управление |
| Создание читателей и менеджеров, пароли и роли | Нет | Да | Да |
| Изменение администратора или назначение роли администратора | Нет | Нет | Да |

Менеджер не может изменить логин, пароль или роль администратора, удалить его или создать нового администратора. Нельзя удалить себя или изменить собственную роль. Смена логина, пароля или роли завершает прежние сеансы этого пользователя; удаление аккаунта также закрывает доступ. Сеансы действуют до 8 часов и сбрасываются при перезапуске сервера.

Прежние admin/viewer keys сохранены для совместимости; это общие входы, и выбор колонок у пользователей одного общего ключа общий. Для персональных настроек выдавайте персональные аккаунты. Прежний ключ администратора остаётся защищённым служебным входом вне списка персональных аккаунтов; менеджер не может изменить его через API. Его ротация выполняется администратором через серверную конфигурацию, как раньше.

В разделе пользователей доступен журнал изменений аккаунтов, устройств, групп и оповещений. Пароли и тела запросов в журнал не записываются.

## Группы и таблица устройств

Группы можно создавать заранее, переименовывать и удалять в разделе «Группы». В карточке устройства нажмите «Имя и группы» и отметьте любые нужные группы. Можно не выбирать ни одной. Удаление группы сохраняет устройства и историю; используемую в оповещениях группу сначала исключите из правил.

Фильтр «Группы» поддерживает несколько флажков и режим «любая» / «все выбранные». Состояния выбираются независимо несколькими флажками. Флажок «Только с проблемами» дополнительно сужает результаты. Отозванные устройства по умолчанию скрыты; включите «Показывать отозванные» или выберите состояние «Доступ отозван».

Основная сортировка: имя, состояние, группа, ОС, последний контакт, проблемы, CPU/GPU, ОЗУ и тома. Направление выбирается отдельно. «При совпадении» задаёт второе поле и направление. Недоступные и устаревшие показатели идут в конце. «Сбросить фильтры» возвращает настройки по умолчанию, включая скрытие отозванных устройств. Фильтры действуют до перезагрузки страницы; колонки сохраняются на сервере отдельно для каждого аккаунта и восстанавливаются на другом браузере.

## Почтовые уведомления

В 0.2.0 реализована почта. Мессенджеры пока не подключены.

1. Настройте SMTP на сервере (ниже).
2. В «Оповещения» создайте почтовый канал: название, до 20 email-получателей, состояние включён/выключен.
3. Создайте правило: устройства, группы, типы проблем, необязательный точный ID датчика, каналы, задержка и уведомление о восстановлении.
4. Нажмите «Тест» у канала и проверьте журнал доставки.

Пример: канал «Дежурные серверной» → нужная почта; правило «PC-01: диск» → устройство PC-01, типы «Том заполнен» и «Предупреждение SMART», только этот канал. Для CPU на том же ПК можно создать другое правило с другим получателем.

Пустой список устройств означает все устройства, пустой список групп — любые группы. Внутри списка достаточно одного совпадения; выбранные устройства и выбранные группы одновременно ограничивают результат. Типы проблем: потеря связи, ОЗУ, температура CPU/GPU, заполненность тома, SMART, ошибка/недоступность датчика. ID датчика берётся из его карточки; он сравнивается точно, без шаблонов. Порог и длительность нарушения настраиваются в общих настройках, задержка доставки — отдельно в правиле.

Один канал получает одно письмо об открытии события по каждому совпавшему правилу. После фактической отправки открытия можно получить письмо о восстановлении. Пересекающиеся правила могут отправить отдельные письма — избегайте дублирующих правил, если это не нужно. Краткие проблемы, исчезнувшие до отправки, не доставляются. Уже активные проблемы также подпадают под новое правило. Устройства на обслуживании и отозванные устройства не отправляют уведомления. При отключении канала/правила ожидающие доставки отменяются; после включения активные совпадающие проблемы снова могут быть поставлены в очередь.

Очередь хранится в SQLite и переживает перезапуск. Обработка — каждые 15 секунд, до 20 писем за проход. На каждую SMTP-сессию установлен общий тайм-аут 30 секунд. При ошибке выполняется до 8 попыток с увеличением интервала; после конечной ошибки доступна кнопка «Повторить». В журнале видны состояние, число попыток, время отправки и безопасный код ошибки. `SMTP_NOT_CONFIGURED` не расходует попытки.

Статус «Отправлено» означает, что SMTP-сервер принял письмо. Конечную доставку в ящик, папку «Спам» и правила провайдера нужно проверять отдельно. В редком случае обрыва соединения после приёма письма SMTP-сервером или аварийного завершения процесса возможна повторная доставка. Не запускайте несколько процессов панели одновременно с одной БД.

## Подключение SMTP

В защищённом `deploy/.env` на своей ВМ задайте:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_MODE=starttls
SMTP_FROM=monitor@example.com
SMTP_USER=monitor@example.com
SMTP_PASSWORD=пароль-приложения-почтового-провайдера
```

Это пример, а не рабочие учётные данные. Для SMTP с непосредственным TLS используйте `SMTP_MODE=tls`, `SMTP_PORT=465`. Поддерживаются SMTP AUTH PLAIN и LOGIN только внутри проверенного TLS-соединения. Незащищённая отправка и отключение проверки сертификата не поддерживаются. Если внутренний SMTP не требует авторизации, оставьте обе переменные SMTP_USER/SMTP_PASSWORD пустыми; TLS всё равно обязателен. Сервер должен разрешать исходящее соединение к SMTP.

Можно использовать `SMTP_PASSWORD_FILE` вместо SMTP_PASSWORD: путь должен существовать внутри контейнера, например `/data/smtp-password`, и быть доступен пользователю node. Не задавайте обе переменные. Такой внешний файл пароля нужно резервировать отдельно: скрипт backup сохраняет БД, ключи и deploy/.env, но не произвольные внешние файлы. Для собственной CA используйте стандартный `NODE_EXTRA_CA_CERTS` с доступным контейнеру файлом и передайте переменную через свой compose override.

После изменения окружения выполните `sudo sh deploy/up.sh`. Пароль SMTP не хранится в браузере или таблицах настроек. Не отправляйте его в чат и не добавляйте реальный deploy/.env, ключи и резервные копии в Git. У некоторых провайдеров нужен отдельный пароль приложения или разрешение SMTP; API/OAuth-провайдеры без SMTP AUTH пока не поддерживаются.

Включены проверки ролей и обхода UI через API, отзыва сеансов, миграции 0.1.x, нескольких групп, индивидуальных колонок, маршрутизации уведомлений, восстановления очереди и SMTP TLS/STARTTLS на локальном тестовом сервере.
